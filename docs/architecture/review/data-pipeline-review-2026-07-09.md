## 4. P0 文档补正草案

> 以下 4 段为可直接粘贴进 v2.0 设计文档对应章节的补正内容。

### 补正 1：5.6.X 章节"异常与边界处理"（新增）

> **5.6.X 异常与边界处理**
>
> **AI 解析失败处理**：当 DeepSeek API 返回非 JSON、超时、识别出 0 只基金，或字段明显异常（如 total_asset 为负或缺失）时，对话气泡状态置为"解析失败"，并提示用户"请重新上传或手动输入"。失败记录写入 chat_history 表，role=assistant，content=错误详情，conversation_type 仍为 screenshot_parse。失败情况下不写入 asset_raw / fund_category_map / asset_snapshot 任何表。
>
> **快照日期校验**：确认面板读取 AI 识别的 snapshot_date，与系统当前日期对比，若差值绝对值 > 7 天，弹出提示框"AI 识别的日期为 YYYY-MM-DD，与系统日期相差 N 天，请确认是否正确"。用户可选择继续或修改。
>
> **is_latest 翻转基准**：同一 snapshot_date 多次入库时，旧记录 is_latest 置为 false、新记录置为 true 的判定基准为 `ORDER BY confirmed_at DESC, id DESC LIMIT 1`。
>
> **并发控制策略**：MVP 阶段不引入悲观锁或分布式锁，采用"前端按钮防抖 + 后端事务默认 READ_COMMITTED 隔离级"的双层防护。
>
> **事务边界**：截图确认入库时，asset_raw 写入、fund_category_map 写入、asset_snapshot 写入必须在同一 @Transactional 方法中执行，任一步失败整体回滚。

### 补正 2：5.6.4 章节"大类确认面板交互规则"末尾（新增）

> **用户修改既有映射的处理规则**：当确认面板中某只基金已在 fund_category_map 命中映射记录（即灰底预填），但用户在下拉选择器中手动修改了大类归属：
>
> - 执行 `UPDATE fund_category_map SET category = ?, source = 'user_correct', confirmed_at = NOW() WHERE user_id = ? AND fund_name = ?`
> - 不新增行（因联合唯一索引 `(user_id, fund_name)` 已存在）
> - `id` 主键不变，便于审计追溯
> - 本次新生成的 asset_raw 行使用更新后的大类

### 补正 3：6.2 章节 `asset_raw` 表结构（修订）

> 在 `category` 字段说明中补充：
>
> `category` 字段枚举值（七项）：货币类、固收类、商品类、A股权益类、海外权益类、港股/大中华类、**余额类**。
>
> 注：余额类（余额宝、余额）虽然不计入六大类资产配置比例，但仍需写入 asset_raw 表以保留逐只基金的持有金额、持有收益、明细记录。汇总表 asset_snapshot.balance_fund 字段保持不变，由 `SELECT SUM(amount) FROM asset_raw WHERE user_id=? AND snapshot_date=? AND category='余额类' AND is_latest=true` 动态计算。
>
> `confirmed_at` 字段补充语义：
> - `created_at`：记录首次写入数据库的时间，用于"我的导入日志"
> - `confirmed_at`：用户点击"确认入库"的时间，用于 is_latest 翻转判定（详见 5.6.X）

### 补正 4：6.7.3 章节末尾"映射优先级规则"（新增）

> **AI 推测与映射表的优先级**：
> 1. 映射表命中：fund_category_map 中存在的基金 → 直接使用映射表中的 category
> 2. 映射表未命中：基金 → 使用 DeepSeek API 本次返回的 category，但标记为"待用户复核"，在确认面板中黄底高亮
> 3. AI 推测与映射表冲突：本次 AI 返回 category ≠ 映射表 category → 以映射表为准；冲突情况可在 Phase 4 的数据校验模块中通过 `source=ai_guess` 但 `confirmed_at` 长期未变 的方式回溯发现

## 9. 评审结论

本次评审发现 **47 个具体问题**（🔴 P0 6 个、🟡 P1 10 个、🟠 P2 11 个、🟢 P3 5 个，其余为补充建议）。其中 6 个 P0 已全部通过文档补正 + 代码动作解决，可直接进入 Phase 1 开发阶段。

最关键的三类风险已被拦截：
