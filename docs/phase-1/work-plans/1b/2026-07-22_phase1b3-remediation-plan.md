## 0. 为什么需要补救

原 1b.3 已打通上传、解析、确认、snapshot_meta 和设为当前快照，但运行时暴露出两类问题：

1. **重大数据加载/绑定 Bug**：解析历史基金数为 0、入库预览各类基金数为 0、实际/目标比例为 0、余额跨日期累加、六大类图混入余额类、类内小计语义错误；
2. **页面呈现未达到产品要求**：首页核心 class 缺少样式，品牌换行、卡片退化为文字、表格层级不清、首页结构未按参考页实现。

补救前缺少页面需求说明书，导致同一“占比”可能指类内、六大类内或总资产内。此次先建立数据口径和页面契约，再进行最小范围修复。

---

## 1. 补救目标

1. 冻结八个侧边栏页面的展示、字段、交互、样式和数据口径需求。
2. 修复当前首页和数据管理页的重大数据加载问题。
3. 按已确认视觉基线美化首页和数据页，使卡片、表格、图表层次完整。
4. 保留并保护所有成熟业务逻辑，尤其是累计/持有收益的现行算法与页面说明。
5. 建立自动化 + 真实数据 Oracle 的可重复验收链路。

---

## 2. 明确不做（范围护栏）

本补救阶段不做：

- 不重写 Vision 解析、AI provider 路由、缓存、重试与熔断；
- 不重写 DedupEngine 的成熟去重逻辑；
- 不改变 confirm 事务、镜像校验和决策 27 的双层语义；
- 不改变累计/持有收益公式、`phase1_simple`、余额宝 fallback 和 Info 弹窗业务说明；
- 不提前实现 Phase 2 月度操作台/资产配置，Phase 3 净值/比例，Phase 5a 季度操作台；
- 不为了视觉效果伪造数据、补 0 或改变收益正负号；
- 不执行破坏性数据库迁移，不直接 SQL 注入 0716 基金数据。

若重大 Bug 的根因位于成熟服务内部，只允许在保护性测试覆盖后做最小修复。

### R1：前端无争议计数与口径修复

优先修复不涉及成熟后端业务算法的前端问题：

1. 入库预览分类基金数改由 `category.funds.length` 派生；
2. 总基金数使用统一汇总函数，加入合计行；
3. 余额类“占六大类”显示 `—`；
4. 六大类图表和配置表严格过滤余额类；
5. 基金分组表列名改“类内占比”，小计显示 100.00%；
6. 分母为 0/字段未知时显示 `—`，不显示假 0；
7. 已知收益为零或正负加和恰好为零时显示 `0.00`，只有全部收益字段未知时才显示 `—`。

**保护边界**：不修改 parse/confirm 返回结构，不改变 DedupEngine。

### R2：解析历史数据加载修复

1. 对 `chat_history.content` 使用现有成熟 JSON 提取能力或等价的最小复用，而不是直接 `readTree` 全文；
2. 支持纯 JSON、Markdown fenced JSON、前后带说明文字；
3. 从 categories/funds 派生总基金数与分类基金数；
4. canonicalize 类别名；
5. 成功但无法恢复计数时返回“未知/数据异常”语义，不伪造 0；
6. 最近操作与解析历史前端展示总数和分类摘要。

**保护边界**：不改变模型原始审计内容，不重新调用模型，不修改解析算法输出。

### R3：当前快照一致性修复

1. 建立一个明确的“当前快照日期”查询入口，复用决策 27 的 `snapshot_meta.is_current`；
2. 余额查询限定该日期，禁止跨日期相加；
3. 收益、基金数和余额 fallback 使用同一个当前日期；
4. 设为当前后，首页所有数据源一起失效重拉；
5. 增加“当前日期为旧日期”的回归用例，防止偷偷回到 MAX(date)。

**保护边界**：不改变累计/持有收益公式和 fallback，只修正输入行集合的日期范围。

### R4：实际/目标比例加载修复

1. `R_category_in_six = categoryTotal / V_6 × 100%`，余额类排除；
2. 当前目标比例从 `user_config.target_ratios` 读取并 canonicalize 港股别名；
3. `deviation = actual - target`；
4. 对已入库但 ratio 为 0 的当前快照，查询展示层可按权威金额重算，避免要求重新上传；
5. 新入库数据如需持久化比例，仅做最小修复并增加事务/镜像回归测试；
6. 六类实际与目标各自合计 100%。

**保护边界**：配置保存不回写历史快照；不实现完整 Phase 2 配置 UI。

### R5：首页与数据管理页视觉补救

#### R5.1 样式 token

- 页面背景 `#F5F5F5`，卡片 `#FFFFFF`，主色 `#0A59F7`；
- 金融正/超配 `#FF4D4F`，负/低配 `#52C41A`，中性 `#8C8C8C`；
- 卡片 8px、`0 2px 8px rgba(0,0,0,0.06)`、`20px 24px`、间距 16px；按钮 4px；
- 金融涨跌 token 与系统成功/错误 token 分离。

#### R5.2 首页结构

1. Header 品牌同行；
2. 总资产 Hero；
3. 六大类、余额类、累计/持有收益三卡；
4. 累计/持有收益沿用现行标准，展示 2 行 × 2 列四个值、Info 标注、算法/快照/基金数；
5. 左环形图、右配置偏差表；
6. 默认折叠基金明细；
7. 口径说明、只读执行总结、快捷入口、最近操作；
8. Loading/Empty/Error 分模块。

#### R5.3 数据页结构

- 上传/解析/预览/确认/快照管理形成明确步骤层级；
- 概览使用卡片，分类和基金明细使用正式表格；
- Modal 表头、按钮、滚动、待确认状态和小屏布局完整；
- 拆分页面样式，避免 `.card`、`.modal-*` 全局互相覆盖。

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 美化时误改累计/持有逻辑 | 先锁定现行响应 fixture 和四值测试，只改 DOM/CSS |

| 未来页面需求造成范围蔓延 | 本轮只做文档完整性，不启用 Phase 2/3/5 功能 |
