**结论**：**PRODUCTION_BLOCKED**——与验收计划 §3 提示一致。

**根因分析**：
1. `fincontrol.ai.vision.minimax.timeout-seconds=300` 配置了 300s，
   但 `VisionModelClient.callRaw(...)` 的 OkHttp client 创建是在
   Spring 启动时一次性初始化（`okHttpClient`，字段 final），
   `readTimeout/writeTimeout/connectTimeout` 写死了 60/120/30 秒。
   造成调用超时不是 300s 而是 60s。详见工作计划 §0.4 遗留问题。
2. 上一次重试 12:08 也出现同样问题（豆包 primary 失败 + minimax fallback 60s timeout）。
   本轮豆包 primary 路径未走，因为 image-count-threshold=2 且 4 张图 → primary=豆包；
   豆包 primary 失败后切 minimax fallback → 60s timeout 超出。

**修复路径**（下一轮 1a.10 P1）：
- `VisionModelClient` 需从 `AiProperties.Provider` 动态读 `timeoutSeconds` ，
  构造 OkHttp client 或使用 `Call.Builder().timeout(...)` 在每次请求覆盖。
- 豆包 primary 失败原因需要完整记录到 OCR 审计日志（不是只记 3002）。
- cache key 需包含 system prompt SHA-256，避免 v2.7.1 命中 v2.5 旧结果。

## 9. 后续债（未消）

### 9.1 余额宝 holding=NULL 被 0 覆盖（**✅ 已修复 2026-07-19 15:46**）

- **现象（修复前）**：DB 写库 `holding_profit=0.00, profit=0.00`，与 ground truth holding=NULL 不一致。
- **根因**：
  - `VisionModelClient` 解析出的 `holdingProfit=0, profit=0`（模型将余额宝“缺列”补 0）
  - `SnapShotConfirmService` `BigDecimal holding = fund.getHoldingProfit() != null ? … : (fund.getProfit() != null ? fund.getProfit() : BigDecimal.ZERO)` 一直 fallback 到 0
- **修复（方案 A：Service 层余额类特例）**：
  - `SnapShotConfirmService.writeAssetRaw` 第 182-202 行加余额类判断：
    ```java
    boolean isBalanceCategory = "余额类".equals(cat.getCategoryName());
    if (isBalanceCategory) {
        holding = null; profit = null;
        cumulative = fund.getCumulativeProfit();
    } else { /* 原 fallback 逻辑 */ }
    ```
  - `schema-h2.sql` 与 `MySQL 1a10-migration.sql`：`profit` 列同步允许 NULL（与 holding_profit 语义一致）
- **验证（2026-07-19 15:46 重跑）**：
  - `mvn test` 套件 238/238 PASS（含新增 `A10P2-S01 confirm_balanceCategory_holdingIsNull`）
  - `02-single-e2e.ps1` 4/4 PASS
  - `03-confirm-e2e.ps1` MySQL user 19999: assetRawInserted=19 / snapshotUpserted=7
  - MySQL 查询：`SELECT holding_profit, profit FROM asset_raw WHERE fund_name='余额宝' AND user_id=19999 AND snapshot_date='2026-07-19'`
    → `holding_profit=NULL, profit=NULL, cumulative_profit=1.89` ✅
  - MySQL 查询统计：`holding_null_count=1`（恰好余额宝 1 行）, `profit_null_count=1`（同余额宝）

### 9.2 路径 B OkHttp timeout 写死 60/120/30（**待修**）

- **现象**：`fincontrol.ai.vision.minimax.timeout-seconds=300` 配置不生效，实际 readTimeout=60s。
- **根因**：`VisionModelClient` 初始化时 `okHttpClient = new OkHttpClient.Builder()....readTimeout(60, SECONDS)…` 直接写死。
- **修复路径**（下一轮 1a.10 P1）：
  - `VisionModelClient.callRaw(...)` 中用 `okHttpClient.newBuilder().readTimeout(timeoutSeconds, SECONDS).build()` 为每次请求动态覆盖；
  - 或者在 @PostConstruct 中从 `AiProperties.Provider` 读取 `timeoutSeconds` 构造 OkHttp client。

### 9.3 豆包 primary 失败原因完整审计（**待修**）

- **现象**：`POST /api/screenshot/parse-batch` 4 图路径中，豆包 primary 失败未记录到 OCR 审计日志。
- **修复路径**：AuditLogJson 增加 `providerFailure: { provider, statusCode, errorMessage, latencyMs }` 字段。

### 9.4 cache key 包含 prompt SHA-256（**待修**）

- **现象**：v2.7.1 prompt 变更后，可能命中 v2.5/v2.6 旧 OCR 缓存。
- **修复路径**：`AiRouter.cacheKey = SHA-256(file bytes) + SHA-256(systemPrompt)`。
